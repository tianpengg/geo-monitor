# Proposal

## Why

完整性审查发现：积压补采没有处理间隔，空闲轮询重复 fsync 状态，异常长行可在一轮读取整个文件，Compose 也没有资源与输出日志上限。现有只读隔离不足以支撑对官网影响可控的判断。

## What Changes

- 每轮新增日志读取设 256 KiB 预算，超长行使用仅内存的扫描游标分轮处理，完整后仅提交一次诊断，不保存原始行。
- 补采默认每批至少等待 0.25 秒，可配置且不能禁用；空闲不改写相同状态，移除已退休代次元数据。
- 本地确认写入失败时恢复内存状态，避免确认位置或解析计数错误累加。
- 采集器 Compose 默认限制 CPU、内存、进程数和 Docker 输出日志，根文件系统只读；保留只读日志、持久状态和主动上报，不挂网站应用目录或 Docker socket。
- 交付功能闭环与配置操作审查报告，修正文档中 HTTP 口径冲突，给出低干扰默认值及停止／更新凭据／重连步骤；零开销与生产容量不作保证。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `incremental-log-collection`: 有界读取、补采让出资源及状态写入行为。
- `self-hosted-deployment`: 采集器资源边界、只读根文件系统和输出日志限制。

## Impact

CollectorConfig、采集循环和 Tailer、采集器 Compose 及示例、相关单元／集成测试和运维文档。协议与状态文件版本不变，不改官网、Nginx、数据库或界面。本机 Engine 仍不可用，新增 Linux 资源验收在 GitHub 隔离环境执行；真实官网仅接收只读短窗口观测，两类证据分别记录，未取得的结果保持待验，不沿用旧验收代替。
