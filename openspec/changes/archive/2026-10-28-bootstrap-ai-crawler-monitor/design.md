# Design

## Context

动机见 [proposal.md](proposal.md)。本变更从只有 OpenSpec 和目录骨架的新项目开始实施；当前实现进度以 tasks.md 为准，验证结果及环境阻塞见 docs/verification.md。不能以目录存在或规划完成作为功能验收。

日志保留和 Nginx 轮转由官网服务器负责。Combined 没有 Host 字段，因此单站独立日志是部署前提；日志中的客户端地址是否可信也取决于网站已有代理配置。

本设计跨服务端、采集器、持久化和后台，包含身份、隐私及故障恢复约束，因此需要独立设计文档。

## Goals / Non-Goals

**Goals:**

- 将一次实际新增日志变成可解释、可去重的后台记录。
- 采用清晰的持久化确认边界，使进程退出和网络重试可以恢复。
- 用独立健康信息表达观测范围、积压、异常及已知缺口。
- 保持单实例部署和明确的模块职责，便于逐步实施与验收。

**Non-Goals:**

- 不为首版引入微服务编排、消息队列、分布式数据库或多租户抽象。
- 不承诺超过源日志保留窗口后的无损恢复，也不从源站日志推断未记录的边缘流量。
- 不在本轮目录和文档交付中创建看似可用的空接口、伪安装脚本或虚假业务数据。

## Decisions

### 1. 单仓库、Python 独立进程和 Vue 管理后台

Python 采用 `src/geo_monitor/` 包布局，`server/` 提供 FastAPI 应用及服务入口，`collector/` 提供独立采集入口，`logparse/`、`crawler/` 和 `storage/` 分别承载解析、核验和数据库访问。根目录通过 `pyproject.toml` 管理包、CLI 与检查配置，`uv.lock` 锁定 Python 依赖，`web/package-lock.json` 锁定前端依赖。

服务端与采集器使用 Python，可在同一包内复用协议约定及日志解析逻辑。采集器作为独立进程和独立容器运行，不能放入 FastAPI 生命周期或 Web worker 的启动任务；导入包不启动后台任务。后台默认单实例、单 Web worker，处理采集接收和查询，不承担文件跟踪。

管理后台使用 Vue 3 + TypeScript + Vite，源码位于 `web/src/`。构建产物由 FastAPI 服务提供，API 使用独立路径前缀；前端路由回退不能覆盖 API 错误。Node.js 只用于开发和前端构建，生产前端由服务端直接提供静态文件。

采用这一组合便于用 Python 实现采集、核验和接口逻辑，Vue 适合当前表单、表格及趋势页面。既有确认、去重和恢复协议继续适用；吞吐能力由实际日志量验证，语言选择不替代可靠性设计。

后台处理正常解析的新增日志，在内存中分类和核验；普通未匹配访问不逐条保存，已识别事件持久化，未知爬虫线索受数量限制地聚合。读取、接收和处理计数独立于爬虫记录，防止“没有爬虫”被误认为采集失败。

```text
Nginx log directory (read-only)
              |
              v
       Collector + state volume
              |
              | HTTPS batches + independent heartbeat
              v
       Server + embedded Web UI
              |
              v
       SQLite local data volume
```

### 2. SQLite 及最小持久化模型

首版使用本机数据卷上的 SQLite，批量写入、短事务及明确的写入协调。含官方 WAL-reset 修复的 3.51.3+、3.50.7 分支及 3.44.6 分支启用 WAL；其他版本采用事务性的 DELETE 模式，避免本机 SQLite 3.50.4 的已知问题。未知供应商回补不猜测为已修复。同步数据库操作使用明确的工作线程或同步处理边界，不在 ASGI 事件循环中长时间阻塞；连接不得跨线程并发使用。查询按网站、发生时间和爬虫建立必要索引。先从事件表直接查询和分组，压测证明必要时再增加汇总表，不预建重复统计存储。

版本依据为 [SQLite 官方 WAL-reset 说明](https://sqlite.org/wal.html#walreset)。模式选择不改变事务、去重、确认或备份约定；容量结果记录实际模式。

| 数据 | 用途 |
|---|---|
| 管理员与会话 | 唯一管理员的密码校验和登录状态 |
| 官网与来源 | 域名、统计时区、网站标识、来源标识及凭据校验值 |
| 批次回执 | 幂等确认、来源文件代次和已接收区间，不保存原始负载 |
| 已识别事件 | 稳定事件标识、发生/接收时间、路径、方法、状态、身份、核验结果及脱敏地址 |
| 采集状态与缺口 | 最新心跳、读取/接收/处理信息、错误计数、已知缺口和覆盖范围 |
| 核验证据快照 | 官方地址清单、来源、版本、抓取时间及有效期限 |
| 未知线索聚合 | 有界的规范化 UA 线索、计数及最近时间 |

明细默认保留 30 天；观测状态、批次幂等信息和来源确认边界不能随明细清理一并丢失。保留来源的确认边界，拒绝已确认旧区间重新产生事件，避免过期明细因重传而复活。清理及备份通过应用或支持的数据库方式执行，不直接复制正在写入的单个数据库文件。

单管理员不等同于低访问量。用户已确认当前先执行合成测试基线，记录数据规模、环境及处理和查询结果；真实日志吞吐量在生产部署前按官网参数复验。PostgreSQL 是容量验证失败后的替代方案，不在目录骨架阶段同时实现两套存储。

### 3. 首次基线、位置和批次确认

- 预检只验证，不改变采集状态。首次正式启用在当前 EOF 建立基线并原子保存；基线落在半行中时，跳过该旧半行后续内容。
- 用设备、inode、内容锚点和持久化代次追踪文件身份，不能只用路径识别文件。锚点只保存摘要，不保存原始行或原始客户端地址。
- Python 采集器以二进制方式读取文件，以字节记录区间和确认位置，拿到完整行后再解码解析；不使用文本流位置或字符数代替日志字节偏移。
- 以 `source_id + generation + line_start_offset` 派生稳定事件标识。内容相同的不同位置有不同标识，文件截断后的新代次不会复用旧标识。
- 采集器状态包含首次基线、文件身份、读取/确认位置、批次标识与区间及必要错误计数。状态文件采用原子替换和持久化写入，不保存事件负载。
- 同一来源按确定顺序发送有数量和大小上限的批次。请求结构或单项协议无效时整批拒绝，避免无明确信息的部分成功。
- 后台先检查凭据、结构和范围，分类与核验不持有长数据库事务；随后在一个事务内处理回执、去重事件、来源确认边界和健康元数据，提交后返回确认。
- 只有新插入的事件参与访问统计；如后续引入汇总表，汇总更新也必须位于同一事务。健康计数使用带序号的快照或幂等结果，不能按重传次数累加。
- 后台成功、响应丢失或本地位置提交失败时均可重传；服务端回执和事件唯一键保证可观察效果不重复。后台已确认的旧区间返回确认，不因记录已过保留期限而再次入库。

这是至少一次发送、幂等处理的协议，不依赖无法跨两端事务保证的“只发送一次”。

### 4. 原始 IP 不额外落盘的恢复路径

未确认内容从官网原有日志重读，采集器只有有界内存缓冲和持久化位置元数据。网络或暂时服务故障采用有退避的重试；认证和协议错误进入可解释异常状态，不跳过位置。

重命名并新建文件时继续跟踪旧文件，直到可读尾部已处理，并发现原路径的新文件。容器重启时在指定日志目录及明确配置的轮转保留目录内恢复文件，不扫描其他网站。部署说明列出支持的轮转和保留方式；首版恢复以旧文件保持可读的原始格式为前提，提前压缩、删除或移出允许目录而无法恢复时，必须报告缺口。

检测到文件缩小或内容锚点变化时建立新代次。copytruncate 可能在复制和截断窗口丢失数据，也可能发生不能完全检测的竞态；显示相应完整性限制，不能因未检测到错误就宣称绝对无缺口。

损坏完整行以位置和错误原因计数，可推进到下一行；相关处理结果必须可恢复，避免进程退出后遗漏诊断。过长行按明确上限拒绝并报告，缓冲不会无界增长。源文件不再可恢复时，记录可确定字节范围、发现时间及原因；无法确定的事件数或时间边界写为未知。

这一路径避免新增含原始 IP 的磁盘队列，代价是离线恢复窗口受源日志保留策略约束。用户原有 Nginx 日志不由本项目复制、清理或改写。

### 5. 识别、官方证据和隐私边界

版本化规则区分 token、运营方、展示名称、用途、官方核验地址和证据状态。首批必需规则与 crawler-identification 规范一致；未知线索不反向推定平台身份。

官方 IP 清单由后台定时获取、校验格式并缓存；只访问规则明确配置的官方来源，不根据上报 UA 中任意 URL 发起请求。每个快照有内容摘要、抓取时间和有效期限；过期或抓取失败时显示证据不可用，不沿用过期证据产生新的已核验结果。旧记录保留其当时使用的证据，不声称当前 IP 清单证明历史时点的地址归属。

接收时原始 IP 只驻留内存，使用可用缓存完成核验后转为部分遮罩地址再入库，不记录批次正文。缺少证据时即时保存降级状态；因为不保留原始 IP，不承诺事后回溯重核历史请求。

安装时确认日志地址是否为真实客户端地址。无法确认时保留 UA 分类，将核验状态设为客户端 IP 不可确认；不通过信任任意转发头来补造客户端地址。

参考依据：

- [Kimi 官方爬虫说明](https://www.kimi.ai/policies/kimi-crawlers)
- [腾讯混元官方爬虫说明](https://hy.tencent.com/polices/hy-crawlers)
- [Nginx Combined 格式](https://nginx.org/en/docs/http/ngx_http_log_module.html)
- [Nginx 真实地址配置](https://nginx.org/en/docs/http/ngx_http_realip_module.html)
- [Nginx 日志轮转](https://nginx.org/en/docs/control.html)
- [logrotate 的 copytruncate 限制](https://github.com/logrotate/logrotate/blob/main/logrotate.8.in)

官方地址是证据来源，不代表部署环境始终可访问。格式、可用性和新鲜度必须在运行时检查；测试使用固定证据样本，不依赖联网结果。

### 6. 登录、采集凭据与接口边界

管理员通过受限部署配置初始化，密码使用带盐的密码散列；不提供公开注册。后台使用可失效的安全会话 Cookie，在 HTTPS 下启用 Secure、HttpOnly 和适当 SameSite，状态修改接口进行同源/CSRF 防护。

随机采集凭据与网站和来源绑定，服务端仅保存不可逆校验值。完整凭据仅在生成时交付，采集器通过受限权限配置文件读取，不使用管理员密码上报。管理查询接口只接受管理员会话；采集接口只接受对应来源凭据。

实施时采用一个明确版本的批量协议，至少包含网站/来源标识、批次标识、文件代次、区间和有界事件列表；返回明确的确认结果和错误种类。预检、日志批次、心跳独立路由；概览和明细共享时间范围解析、权限校验及分类定义。

### 7. 健康状态与统计时间

默认每 10 秒或到达批量上限发送日志，每 30 秒发送心跳，超过 90 秒未收到有效心跳显示断连。后台页面每 30 秒刷新，使正常无积压条件下新增完整日志在 60 秒内可见。

分别记录 last_heartbeat_at、last_log_received_at、last_processed_at、最后成功读取和最新错误。健康状态按连接、读取、解析、处理及覆盖多个维度表达，不用一个布尔值覆盖所有含义。网络断开先表示观测中断；补采成功后可以恢复覆盖，只有确认无法恢复时才记为永久缺口。

事件时间按日志时区转换为 UTC 保存，接收时间独立保存。官网统计时区默认为 Asia/Shanghai；今天、近 7 天及近 30 天按含今天的自然日计算，日期查询使用开始包含、结束不包含的统一边界。

页面数按去除查询参数后的路径计算，保留大小写及不同路径，不额外进行业务 URL 合并。原查询参数、remote_user 和 referrer 不作为持久化字段。已识别请求按 UA 身份统计，同时单独给出核验分布；未知线索不进入已知平台统计。未观测时段和缺口分别绘制，不补零。

### 8. 部署与迭代顺序

`deploy/` 提供控制台 Compose、采集器 Compose、镜像构建及配置示例，实际容器验收结果独立记录，不能以文件存在作为运行通过依据。镜像封装 Python 运行环境和锁定依赖，宿主机不要求另行安装 Python；Vue 前端在构建阶段生成静态产物。服务端数据库使用本机持久化卷；采集器挂载指定日志目录为只读，状态目录独立可写。跨机通过 HTTPS 主动上报，不开放采集器入站端口。

代码实现依次交付：最小登录与官网配置、真实新增日志到明细的链路、重试去重及轮转、健康状态、概览和筛选、完整安装与部署验收。Python 单元测试使用 pytest，位于 tests/unit 并随模块变更交付；跨进程和故障恢复场景放入 tests/integration，测试样本放入 tests/fixtures，不写入真实日志或凭据。

## Risks / Trade-offs

- 源日志保留不足或旧文件不可恢复 → 安装说明给出补采前提，预检展示相关信息，恢复失败记录已知缺口。
- copytruncate 存在固有丢失窗口 → 优先采用重命名并重新打开日志的轮转方式，清楚展示兼容边界。
- SQLite 可能受真实站点写入量限制 → 当前记录合成测试基线；生产部署前补充峰值行数及平均行大小，执行与实际量级匹配的批量接收及 30 天查询压测；未达标不得宣称满足该负载。
- 官方地址清单可能无法访问或已变化 → 使用带期限的快照并降级显示，保留核验时依据，不将不可核验等同于不匹配。
- 脱敏后无法重新核验历史 IP → 核验在接收阶段完成，记录证据版本，界面说明历史核验能力边界。
- 标准日志不含 Host，代理地址可能不是客户端 → 要求独立日志并确认真实地址配置，不能仅依靠域名配置推断。

## Migration Plan

1. 初始阶段建立结构及规划，当前按 tasks.md 实施和验证；正式能力规范在相关验收完成后同步，未通过项保持未完成。
2. 实施时建立版本化数据库迁移、构建和配置示例，先验证最小端到端链路再增加其余能力。
3. 在受支持的 Linux / Docker 环境执行全部首版验收；安装说明记录实际日志量级、源日志保留前提和验证结果。
4. 上线前备份配置、数据库和采集器状态；回退仅使用与数据库版本兼容的镜像，涉及不兼容迁移时从匹配备份恢复，不自动执行破坏性降级。
5. 停止或重建容器保留数据卷。主动重置来源状态必须明示新的基线及覆盖变化。
6. 实施任务及验收完成后同步正式规范并归档本变更，验收记录保留测试输入、环境和生产参数后补的边界。

## Open Questions

- 用户已确认先使用测试基线，生产参数稍后补充。本轮使用 3 万条合成已识别事件、30 天分布和 1000 个路径；每条来源区间模拟为 256 字节，按 1000 条一批进行本地处理及查询检查，结果见 docs/verification.md。这些数值不是实际峰值或平均日志行大小。
- 目标官网的峰值日志行数与平均行大小在生产部署前记录，并据此执行容量复验及确认批次参数。
- 实际源日志保留天数、未压缩保留窗口和轮转命名在生产部署前记录，用于向管理员准确说明可补采时间；临时日志恢复测试不代表生产保留窗口已验收。

这些环境参数不改变当前确认/重试协议；当前不预设吞吐承诺或无限期补采承诺。若实测需要改变存储或兼容范围，先修订相应设计与任务。
