## 本轮发现与修复

| 问题 | 修复及验证 |
|---|---|
| 积压时成功后直接继续，可能持续占用 CPU / IO | 每批使用可中断正等待，`catchup_pause_seconds` 默认 0.25 秒、允许 0.05–30 秒；保留失败退避和独立心跳 |
| 一条异常长行可能持锁读到文件尾 | 每轮新增源数据读取预算 256 KiB；分轮扫描超长行，只在完整行尾确认并计一次诊断；重启从原确认位置分轮重扫 |
| 相同状态反复写临时文件及 fsync | 缓存最后成功序列化状态，无变化不写；空轮询和空缺口确认的 fsync 回归通过 |
| 退休文件代次元数据长期积累 | 清理已退休代次和已消失的初始忽略文件标识，未确认缺口独立保留 |
| 本地保存失败后内存确认位置及诊断已改变 | 写失败恢复旧内存状态，保留待确认批次，重试不重复增加解析错误；服务端仍按稳定标识去重 |
| 默认容器没有资源和输出日志上限 | 配置 0.25 CPU、128 MiB 内存、64 PID；根文件系统只读，16 MiB `/tmp`；输出日志每个 5 MiB、最多 2 个；后续 Linux CI 已核对实际执行 |
| README 仍称 HTTP 仅限开发环境 | 修正为已授权的 HTTP / 可选 HTTPS 口径；后续双协议实际验收已完成并独立记录 |

读取预算不包括文件元数据检查和每个文件至多 128 字节的身份锚点读取，因此不能解释为整机磁盘 IO 的硬限额。预算和间隔也不构成生产吞吐承诺。持续增长且未结束的超长行不保存原文；扫描进度仅在内存，重启会重扫，已确认位置保持安全。

## 对官网的边界

- 独立进程和容器，不在 Nginx 请求处理、应用中间件或 FastAPI worker 中采集；不与官网写入方共用应用锁。
- 日志目录及配置只读挂载，状态使用独立可写卷；不监听入站端口，不使用 host 网络、特权容器或 Docker socket。
- 采集器停止、网络失败或控制台不可达，官网仍按原方式写源日志。补采受源日志保留窗口约束，不能通过删除状态解决连接问题。
- CPU、内存和日志限制已由 Linux CI 核对实际 cgroup 与引擎配置，真实 OOM 后自动恢复和独立源站持续服务通过；真实官网另有有限窗口只读观测，没有生产故障注入或停采对照。
- 同机读取仍消耗 CPU、内存、磁盘和网络。应用节流不等于磁盘带宽硬隔离；控制台同机运行也会竞争资源。建议控制台分机，采集器保守启动后观察官网延迟和错误率。
- 安装会下载依赖并构建镜像，构建开销不受采集器运行限额约束。官网低峰安装，资源紧张时先在其他机器构建兼容镜像，再安排部署。

## 配置是否方便

日常使用不需要为每个模型安装不同采集器。控制台配置一次官网，采集器安装时主要输入两项：该官网独立日志的绝对路径、后台生成的采集凭据；后台地址和网站 / 来源标识由命令带入。爬虫规则、时区、内容目录均在后台维护。

建议按以下顺序接入：

1. 服务器准备 Docker / Compose，确认控制台实际访问地址和端口，执行 `bash scripts/deploy.sh` 部署控制台。
2. 登录后保存官网域名、统计时区和客户端 IP 判断。不确定日志 IP 来源时选择“不确定”，仍能采集和识别 UA。
3. 找到该站独立的 Nginx Combined 日志；混合多站日志不能只靠后台域名拆分。不要为了安装执行 `chmod 777` 或改写日志格式。
4. 在日志所在服务器执行后台提供的安装命令，按提示输入日志绝对路径和隐藏凭据；预检通过后启用。
5. 官网产生新请求后，核对最后心跳、最后接收时间、处理状态和新增请求；没有匹配到爬虫但健康正常属于有效结果。
6. 验证停止 / 重连保留原状态；凭据更新后需要重新输入新凭据或更新 `collector.json` 再重建容器，单独点重连不会自动取得新凭据。

高级限额、停止及重连命令见 [运维说明](operations.md#采集器运行边界与资源配置)。安装脚本不会替管理员处理公网、防火墙、1Panel 代理、源日志权限或轮转保留策略；这些仍是接入前置条件。
